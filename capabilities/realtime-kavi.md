# Real-time Kavi (v0.2)

## TL;DR

An always-on Python runtime on Kavi's Mac (`kavi-runtime/`), triggered by MS Graph email webhooks. Closes three loops: real-time pipe (email → judgment → iMessage in ≤15 min p95), skip-correction capture (Megha texts "you missed X" → Kavi acks within 60s + logs), learning-from-correction (after 2+ same-pattern corrections, Kavi proposes an Examples row to `capabilities/inbox-to-task.md` for one-tap approval). Runtime uses Anthropic Python SDK (Sonnet 4.6 with prompt caching, ~$15/mo expected, $30/mo spend cap).

## Why now

- **What's broken:** Pre-runtime, Kavi was a set of manual slash commands. When Megha replied to a Kavi iMessage question, nothing happened until she manually re-triggered the scan. No acknowledgment, no real-time MS To Do update, no follow-up. MS To Do is not yet her source of truth, and she stops trusting Kavi.
- **Who feels it and when:** Megha, every time she replies "1 yes" to a Kavi question and the task doesn't appear in MS To Do for hours. Every time she texts "you missed the Boonli email" and there's no acknowledgment. Trust collapses fast in this gap.
- **Why now (Doshi):** Leverage. v0.2 is the realization of CoS Step 1 ("Megha solo loop with full Q&A"). Step 1 today is shipped-but-friction-fatal. v0.2 closes the loop AND adds the learning-from-correction flywheel that compounds Megha's judgment into Kavi's over time.

## Behavior (the spec)

What the always-on runtime should do:

**Real-time pipe (good):**
- New email arrives → MS Graph webhook fires → kavi-runtime fetches message + thread (~3-5 messages via `conversationId`) → runs `email-to-tasks` against Anthropic API → semantic-dedup check against last ~25 active tasks → push to MS To Do (silently if high-conf, with iMessage if low-conf).
- **Two summaries per day, not four.** Morning digest (7 AM) and evening rollup (9 PM). Updated 2026-04-29 — the prior 4-hour cadence (11 AM / 3 PM / 7 PM ticks) was noise, not signal; Megha checks MS To Do directly when she wants the live state.
- **Priority senders no longer trigger immediate iMessage.** Updated 2026-04-29 — task gets created in MS To Do; surfaces in next summary like everything else. The <!-- private:rtk-001 -->"interrupt now for Dana Park"<!-- /private --> pattern was making Kavi feel reactive instead of curated.
- Quiet hours 11 PM - 7 AM: queued messages roll into 7 AM digest. No Kavi-initiated iMessages.
- Reply to a queued question (free-form, parsed by LLM as of v0 conversational build): resolve task, push to MS To Do, send confirmation iMessage within 60s. Ask Megha to clarify if reply doesn't pin to one open question with high confidence; never silently guess.

**Skip-correction (good):**
- Unsolicited iMessage from Megha that doesn't match a queued question → `correction-classifier` Anthropic prompt parses free-text → extracts `(type, target, reason)` → appends to `corrections.jsonl` → acks within 60s ("Got it. Logged. I'll watch for school vendor noreplies going forward.").
- On next `email-to-tasks` call, kavi-runtime injects unapplied corrections matching the email pattern into prompt context. Sets `applied: true` once consumed.

**Learning-from-correction (good):**
- Scheduled job every 6 hours scans `corrections.jsonl` for unprocessed patterns.
- 2+ corrections of same `(type, sender_pattern)` → iMessage Examples-row proposal: *"I've seen 'school vendor noreply' as missed-action 3 times. Add this Examples row: ****\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*noreply@boonli.com****\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\* / Boonli school lunch menu / action despite noreply prefix → create task? 1 yes / 1 no."*
- "1 yes" → append row to `capabilities/inbox-to-task.md` Examples table, write decision to changelog, confirm via iMessage.
- "1 no" → increment threshold for that pattern to 3 corrections before re-proposing.
- Promotion from Example to Hard rule is out of scope for the auto-loop. Megha makes that call manually.

**Bad (failure modes — see deeper detail in changelog 2026-04-28 entries):**
- Classifier misreads non-correction as correction → spurious MS To Do change.
- Fuzzy `find_task_by_title` finds wrong task → silent corruption.
- `wrong_title` rewrites a task Megha wanted to keep → irreversible.
- iMessage references multiple tasks ambiguously → Kavi picks one, others go unaddressed.
- `corrections.jsonl` grows unbounded → injection cost dominates.
- Spend cap trips during quiet hours → Megha doesn't learn until manually checking next morning.
- Intent classifier false-negative on resume → "you can run again" misroutes to correction classifier → no resume.
- Backlog drain on resume re-trips spend cap immediately → infinite pause-resume loop.
- A time-boxed "go quiet" never expires → email→task silently gated for days while the digest/reply path keeps talking (the 2026-06-27 stuck-pause). Mitigation: every quiet window carries a `paused_until`, auto-resumes when it elapses, and a watchdog alerts if it gets stuck.
- Webhook flood throttle starves real traffic on a busy morning → tasks delayed up to an hour.
- Token cap on a legit long thread → silent drop. Mitigation: iMessage names the skipped subject so Megha can manually create a task.

## Metrics

In addition to all `inbox-to-task` metrics (precision, owner accuracy, recall, dedup, etc.), v0.2 adds:

| Metric | Target | Why |
| --- | --- | --- |
| Time-to-first-action (email arrival → iMessage in Megha's hand) | ≤15 min p95 | Closes the silence gap; the trust-erosion driver. |
| Reply-to-update latency (Megha replies → MS To Do reflects + confirmation sent) | ≤60 sec p95 | Closes the "did my reply land?" friction. |
| Daily Active Megha (DAM) | =7/7 days/week | If Megha stops talking, Kavi failed. |
| Corrections logged per week | 3-5/day during learning phase | Engagement during trust-building window. |
| Repeat-error rate (same correction-type within 7d) | <10% | The data flywheel KPI: is Kavi actually learning? |
| Correction → Examples-row update rate | ≥40% | Quality of corrections; the rest are one-offs. |
| Precision lift attributable to corrections | +5pt rolling precision per month during learning phase | Direct measure of HITL data flywheel impact. |

**Goodhart watches:**
- DAM gamed by perfunctory replies → counter-metric: % messages ≥3 words.
- Repeat-error rate gamed by Kavi avoiding corrections altogether → counter-metric: total corrections logged should stay 3-5/day, not collapse.
- Correction → Examples-row rate gamed by approving low-quality proposals → counter-metric: precision after Examples additions should not regress.

## Guardrails (circuit breakers)

Three active as of step 12 (shipped 2026-04-29). Two deferred.

**Active in v0.2:**

| Guardrail | Trigger | Action |
| --- | --- | --- |
| **Monthly Anthropic API spend** | Cumulative Anthropic cost this Pacific calendar month >$30 (2x expected $15). Tracked in a persisted running-total file (`state/anthropic_spend.json`), incremented by the runtime after every Claude API call and priced per model via `kavi_runtime/pricing.py`. | Set `auto_runs_paused=true` in `state.json`. iMessage Megha (or queue for 7 AM if quiet hours). All inbound email queues to `paused_email_queue`. Resume requires LLM intent classifier to confirm Megha's iMessage means "clear pause." On resume: spend-cap bypass set for rest of calendar month **only if this month is still over the cap** (a pause left over from a prior month grants no bypass, so the cap stays armed); backlog drains, limited to mail received in the last `drain_max_age_days` (7) days, and accounts in `drain_hold_accounts` stay queued untouched. |
| **Webhook flood** | >50 MS Graph events/hour, rolling 60-min window | Throttle to 1/min via deferred queue. iMessage Megha (debounced max 1/hr). No pause. |
| **Per-call token blowup** | Single `email_to_tasks` call's estimated input >50K tokens (char/4 pre-check) | Halt that call. Log `status=token_blowup`. iMessage Megha naming the email subject. No pause. |
| **API balance exhausted** | Sonnet call returns `400 invalid_request_error` with `credit balance is too low` substring | Set `auto_runs_paused=true` (same as spend cap). iMessage Megha via Outlook fallback (since Sonnet is the failing surface and persona-LLM-outbound is also down). Queue all inbound email to `paused_email_queue` so refill triggers replay. |
| **User-requested quiet window** (added 2026-07-14) | Megha tells Kavi to go quiet (intent parser classifies a `pause` intent) | Set `auto_runs_paused=true`, `paused_reason=user_requested_quiet`, and a **time-boxed `paused_until`** (UTC ISO) computed from the request — an explicit sub-day duration ("for an hour", "30 minutes") or, by default, the next 7 AM Pacific — **hard-capped at 24h**. Inbound email queues to `paused_email_queue`. **Auto-resumes** once `paused_until` elapses (the 5-min `quiet-window-watchdog` scheduler job calls the normal resume → dedup + spend-guarded drain + clear). Resume can also be triggered early by an inbound "resume". |

**Why time-boxed (the 2026-06-27 stuck-pause):** a quiet window used to have NO end time and only an inbound "resume" could clear it, so a "quiet until tomorrow morning" became a permanent silent outage — 17 days, 912 emails queued, zero tasks, masked because the digest/reply path is (correctly) not gated by the pause. Every quiet window now self-expires within a day. Only `user_requested_quiet` auto-resumes; spend/webhook/api pauses stay down until the underlying condition clears + Megha confirms (auto-resuming a spend pause would instantly re-trip — the drain-retrips-cap loop above).

**Stuck-pause liveness (added 2026-07-14):** the backstop for the backstop. The `quiet-window-watchdog` also alerts Megha ONCE per episode if a `user_requested_quiet` pause is un-expirable (a legacy pause with no `paused_until`) or overdue past a 1h grace (the resume job somehow not firing). This is the online liveness signal the earlier "invocation-floor" alarm lacked without its false positives: it fires only on a genuinely stuck quiet pause, never on a merely-quiet inbox (silence is not failure). The `/status` "This month's Anthropic spend" field now reports the **real** `paused_reason` instead of a hardcoded "paused-by-spend-cap" that made a quiet pause masquerade as a spend trip.

**Long-pause liveness, every reason (added 2026-09-23):** the same watchdog alerts Megha ONCE per episode when a spend, webhook, or API pause has lasted over 24h ("Heads up: I've been paused for N days (reason), so new email isn't becoming tasks"). Alert only; it never auto-resumes a non-quiet pause.

**Pause-state resume detection:** LLM intent classifier (NOT keyword match). Every iMessage from Megha during pause routes through Sonnet first with pause context. Output: `{intent: resume | not_resume, confidence: high | low}`. Ack restates the action ("ok, I'm running again from the $30 spend pause") so misreads are visible. Cost ~$0.003/call; pauses are rare; total cost rounding-error.

**Security hardening (shipped 2026-05-05):**

The five rows below encode the threat model approved during Max's Outlook-onboarding consent conversation. Five attack vectors against an always-on LLM agent that reads untrusted email and sends iMessage: prompt injection from inbound email, social-engineering of the persona, accidental leakage of financial / health / account-bound content into an outbound, accidental leakage into a durable-fact write that later replays into context, and inbound-from-an-impostor (an iMessage from a handle that isn't in `household.md`). Each row references an existing mechanism in the runtime. Initial spec landing 2026-05-05 morning was `proposed`; runtime build shipped 2026-05-05 evening (this dispatch). All four deterministic gates run in `kavi_runtime.outbound_scanner`; financial-domain redaction lives in `kavi_runtime.financial_domains`; the canonical send wrapper in `kavi_runtime.handlers._send_imessage_with_fallback` routes every persona-voiced outbound through both gates before BlueBubbles SEND.

| Guardrail | Trigger | Action |
| --- | --- | --- |
| **Outbound iMessage recipient allowlist** | iMessage SEND attempted to a handle not in `household.md` | Block send; log to `outbound_blocked.jsonl` with `reason: unknown_recipient`; alert Megha via the existing healthchecks-style alert path. |
| **Inbound iMessage sender allowlist** | iMessage webhook payload from a handle not in `household.md` | Discard before classification; log to existing inbound JSONL with `discarded_unknown_sender: true`; do NOT invoke the action-intent classifier or the persona on the payload. |
| **Outbound content scanner** | Outbound iMessage, MS To Do task body write, durable-fact write, or future outbound email contains a credit-card / SSN / routing-number / account-number regex match | Block the outbound; log to `outbound_blocked.jsonl` with `reason: sensitive_pattern_<pattern_name>`; alert Megha. The scanner runs AFTER the persona composer and BEFORE the actual SEND or POST. |
| **Task body redaction** | The inbox-to-task path creates a task from an email matching financial-domain sender patterns (banks, brokerages, insurers, IRS, schools collecting payment) | Body is paraphrased only — sender plus subject summary plus "balance available, see source email." Verbatim numerics and account identifiers never enter the task body. |
| **Durable-facts write filter** | `durable_facts.record_fact` called with `fact_text` containing a sensitive-pattern regex hit | Reject the write; return `(None, blocked_reason)`; log to `outbound_blocked.jsonl` with `reason: sensitive_pattern_<pattern_name>`. |

## Architecture

**Output composition rule.** Every user-facing reply Kavi sends is composed by an LLM call. Deterministic steps (intent classifiers, exact-title matchers, dedup checks, action API calls) sit UPSTREAM of the LLM and feed it richer context; they never own the prose Megha or Max reads. Cold-fallback templates fire only when the LLM is unreachable (Anthropic 529, network down, budget cap) and label themselves as fallback. See `kavi-persona.md` Principle 7 for the full statement.

```
[MS Graph] --webhook--> [Tailscale Funnel] --> [kavi-runtime on Kavi's Mac]
                                                  |
                                                  +--> Anthropic API (Sonnet 4.6) --> judgment
                                                  +--> MS Graph SDK --> MS To Do CRUD
                                                  +--> BlueBubbles HTTP API --> iMessage send
                                                  +--> append to corrections.jsonl
                                                  +--> append to evals/runs.jsonl

[BlueBubbles webhook on Kavi's Mac, local] -----> [kavi-runtime] --> reply processing
                                                                  --> correction processing
```

**Public ingress:** <!-- private:rtk-011 -->`https://kavi-mac.tailnet-0000.ts.net`<!-- /private --> (Tailscale Funnel; chosen 2026-04-28 over Cloudflare Tunnel because Megha doesn't own a domain).

**Multi-account auth (added 2026-05-05 evening, Step 3 of the build order).** The runtime authenticates against every household Microsoft account discovered from `household.md` (currently Megha + Max). Each account holds its own MSAL token cache at `~/.config/kavi/tokens/<email>.json` and its own MS Graph webhook subscription state at `~/.config/kavi/subscriptions/<email>.json`. Webhooks fire against a single endpoint (`/graph/notifications`); the router maps the inbound `subscriptionId` back to the originating account via the per-account state files and threads that account through `email_arrived` so every Graph call uses the right token plus the right per-account view of the shared MS To Do list (Microsoft assigns a different list ID per account on shared lists; the runtime resolves the list by display name `McMullen-Jain Shared` on first use per account and caches it). New accounts are added interactively via `python -m kavi_runtime.add_account <email>`; the scheduler's subscription-renewal loop iterates every configured account and silently skips any account whose token is not yet cached so the missing account never crashes the rest of the runtime.

**Runtime topology:**
- `kavi-runtime/` directory at HomeOS root. Python service with FastAPI for webhook receiver.
- Modules: `server.py` (webhook receiver), `handlers.py` (event handlers), `scheduler.py` (cron jobs), `claude_client.py` (Anthropic SDK wrapper with prompt caching), `graph_client.py` (MS Graph SDK), `bluebubbles_client.py` (BlueBubbles HTTP), `state.py` (JSONL appenders, state readers).
- `kavi-runtime/skills/` — skill prompts ported from `.claude/skills/` as plain text.
- `kavi-runtime/launchd/com.megha.kavi.plist` — launchd service for auto-start on boot.
- API key at `~/.config/kavi/.env` on Kavi's Mac (perms 600). Funded $20 prepaid; auto-recharge OFF.
- **Headless operation:** Kavi's Mac runs lid-closed in a fixed always-on location. Type-C HDMI dummy plug (installed 2026-05-02) satisfies macOS's "external display attached" check, preventing display/clamshell sleep.

**Trigger model:**

| Trigger | Action | Why |
| --- | --- | --- |
| New email (MS Graph webhook) | Run `email-to-tasks` immediately on email + thread | Token-efficient, closes time-to-first-action |
| Email is low-confidence | Immediate iMessage to Megha | Closes silence-after-reply gap |
<!-- private:rtk-002 -->| Email matches priority sender (e.g., Dana Park) | Immediate iMessage regardless of confidence | Megha-named pattern |<!-- /private -->
| Email is high-conf, not priority | Auto-push to MS To Do, queue for next summary | Avoid spam |

## Action-claim correspondence

Added 2026-05-07 (action-hallucination triage) per the template requirement for `runtime` capability_type. Realtime Kavi hosts every other capability's composers; whenever one of those composers produces user-facing text, this capability owns the runtime-side gate that enforces Principle 7 of `capabilities/kavi-persona.md`.

**Action verbs that require grounding (canonical list).** `sent, marked, added, dropped, deleted, removed, filed, done, resending, resent, delivered, scheduled, queued, completed, closed`. Hosted in `kavi_runtime/structural_checks.py::ACTION_VERBS_REQUIRING_GROUNDING`. The same list lives in the kavi_conversation skill ban, the post-action composer's groundedness rule, and the Friday weekly metric. Updates land in all four surfaces in the same patch.

**Per output kind (hosted composers):**

- **Conversational reply (`compose_conversational_reply`).** Composer has NO tool result in scope by design. If output contains any verb in the list → G-A1 fails. Runtime behavior on fail: `_handle_correction` drops the offending text and ships an `alert_fallback` ("Got your message — I caught myself about to claim an action I didn't actually run...") instead. The hallucinated original is logged to the eval surface (`kind=conversational_g_a1_blocked`) but never reaches Megha.
- **Action layer post-action reply (`compose_post_action_reply` / `compose_batch_action_reply`).** Composer is downstream of the MS Graph PATCH/POST. The runtime builds `actions_executed[]` with verified `{result, target_title, failure_reason?}` and passes it to the composer. G-A1 passes when at least one entry has `result=success`. On all-failure batches, the composer must NOT use action verbs; the cold fallback ("Couldn't mark any of the X done — MS To Do hit an error. Retry?") is honest by construction.
- **Coordination outcome (`compose_coordination_outcome`).** Branch determines whether action verbs are allowed. `4b_will_grab` with a non-null `task_id_if_created` permits "added" / "scheduled"; `4b_will_grab_task_create_failed` (the failure-aware sibling, added 2026-05-07) forbids them and the composer ships a heads-up reply instead.
- **Q&A-ack and correction-ack deterministic templates (`_handle_q_and_a_reply`, `_handle_correction`).** Templates contain action verbs ("Dropped:", "added", "Removed", "Renamed", "Retagged"). Runtime sets `context.tool_grounded=True` on the outbound row ONLY when the Graph call returned without exception. On a swallowed exception, `tool_grounded` stays False and G-A1 fails. This is the deterministic-path analog of the LLM-composer's `actions_executed` mechanism.

**Runtime behavior when grounding is missing (per kind):**

| Kind | On G-A1 fail |
| --- | --- |
| `conversational` | Drop original; ship `alert_fallback`. Hallucinated text logged but not sent. |
| `post_action_reply` / `compose_batch_action_reply` cold fallback | Cold-fallback string built in handler chooses verbs based on `actions_executed[]` shape, so action verbs are not produced when no successes exist. |
| `qa_ack` / `correction_ack` | Logged as G-A1 fail; row ships today (the deterministic ack is small enough to tolerate the rare swallowed-exception case). Tightening to drop-on-fail is a future iteration. |
| `coordination_outcome` | Logged as G-A1 fail; row ships. The composer is persona-voiced and the branch identifier already encodes failure shapes; runtime drop is over-engineering today. |

Weekly review surfaces the action_claim_correspondence_rate during the HTML-viewer open-coding pass over the past week's outbound traces; threshold is 100%. Below 100%, failing rows surface for axial review.
